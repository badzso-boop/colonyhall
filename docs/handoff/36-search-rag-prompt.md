## Decisions (binding)

- **Two embedding spaces:**
  - **text** (chat, wiki, decisions, summaries): a small multilingual model on the **Raspberry Pi 3B** (e.g. `multilingual-e5-small`, 384 dims), always on; the history is backfilled on the PC with **the same model and version**;
  - **code**: a code-specific embedding model on the **PC's GPU** (RTX 3060 12 GB, WSL2), e.g. `jina-embeddings-v2-base-code`, `nomic-embed-code` or `bge-m3`; used at index time and at query time. **The PC is not always on**: code semantic search works only while it is.
- **Reranking for both:** text on the **homelab** (a multilingual cross-encoder), code on the **PC's GPU** (a reranker that handles code). When a reranker is down, search still answers without it and says so.
- **When the PC (the GPU) is off:** every tool that needs it returns a **short, meaningful error** quickly (no hang, no timeout wait), e.g. `code semantic search unavailable: the GPU machine (pc-wsl) is offline; keyword code search and CodeGraph still work`. The server knows the GPU services' state (from the PC guard's host report and a health check), shows it on the status page, and every agent and machine gets the same answer.
- **Code chunking:** per symbol (function, method, type) along CodeGraph's boundaries, plus one entry per file (its role in one sentence). What is embedded: the qualified name, the signature and a short description; never the body (CodeGraph returns the source when needed). The description is the doc comment when there is one, otherwise **one sentence generated by the local model on the GPU**, cached by content hash; only changed symbols are re-indexed.
- **Hybrid search:**
  - text: Postgres full-text with the `hungarian` and `simple` configurations, plus pgvector;
  - code: **identifier splitting** (`parseAgyReset` → `parse agy reset`, `max_concurrent_runs` → `max concurrent runs`) in the keyword index, plus **trigram** (`pg_trgm`) for typos and partial names, plus pgvector;
  - both merged with Reciprocal Rank Fusion, then reranked.
- **Access control, strict, at query time:**
  - text: channel membership; DMs only for their members; the round 38 colleague rules;
  - code: an **agent sees only code inside its own folder grants**; **admins see every machine's code**; the colleague sees only his own folders;
  - applied in SQL **before** ranking, never by filtering a top k afterwards.
- **pgvector stays in the shared Postgres** (`homelab-shared-postgres` runs the `pgvector/pgvector:pg16` image; `legymernok` already uses `vector` there). It is enabled once, only in the `colonyhall` database (`CREATE EXTENSION vector`, superuser, by Norbi). No image change.
- **Retrieved text is data, never instructions** (framed like chat messages). **Everything is logged.** **The agent decides** when to search: a tool, not a rule.

## 36a. Text sources

1. **Storage and the embedding port:** the migration as approved (the migration does not create the extension; it fails with a clear message if `vector` is missing); an `Embedder` port with `http` (the Pi, `COLONY_EMBED_URL`) and `fake` adapters; a `Reranker` port with `http` (the homelab, `COLONY_RERANK_URL`) and `none`. Timeouts, batch limits, the model name and version checked against the stored ones. Store tests in `internal/storetest` for memory and Postgres.
2. **Indexing:** a consumer on the event log creates, updates and removes chunks (message created, edited, retracted, deleted; wiki appended, deleted; decision recorded; compaction done, regenerated); chunks are written with `embedding = NULL` and an embedding worker fills them in batches, with retry and backoff; **when the Pi is down, keyword search keeps working**. `colonyhall rag-backfill` (resumable, idempotent by content hash, a progress line, a dry-run that only counts) and a re-embed command.
3. **Search:** one `Search` use case (`query`, `mode` `keyword` | `semantic` | `hybrid`, default `hybrid`; filters; `limit` default 8, max 20; the caller); access control in both legs' SQL; RRF, then the reranker on the top 50. Each result: kind, snippet (matched words for keyword hits), source reference, author, time, the score of each stage.
4. **Interfaces:** the MCP tool `search` for every agent (sandboxed ones through their Colonyhall MCP access), results framed as data; `GET /search` (contract first); a short hint in the shared agent rules (not a rule).
5. **PWA:** a search field (the command palette's search box opens it), results grouped by source, matched words highlighted as text, a "Kulcsszó / Jelentés / Hibrid" switch, and the stage scores for admins.
6. **Logging and status:** `search_log`; the status page: queue length, last embed, Pi and reranker reachable, model and version.

## 36b. The code index

1. **The GPU services port:** a code `Embedder` and `Reranker` reached as decided in part 0 (preferably through the PC guard's host connection); availability tracked from the host report and a health check; **the short error** when the GPU machine is off, in the MCP tool, in `GET /search` and on the status page.
2. **Indexing on the PC:** the guard (on the GPU machine) walks the indexed repositories (round 39's list), takes symbols from CodeGraph, fills descriptions (doc comment, or one sentence from the local model, cached by content hash), embeds them on the GPU, and sends the chunks to the server; incremental on change; **only folders inside agents' grants** on that machine are indexed.
3. **Code search:** `search` gets `scope: code` (and `scope: text`, default both where allowed); hybrid with identifier splitting and trigram for the keyword leg; the code reranker; access control by folder grant (agents strictly their own, admins all, the colleague his own).
4. **An MCP tool for round 47:** `search_code` (or `search` with `scope: code`) returning name, file, line, signature, description and score; CodeGraph remains the way to read the source.
